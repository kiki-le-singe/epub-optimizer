## Fixed: an invalid character reference could be rewritten as a wrong character

When an XHTML document contains HTML named references such as `&nbsp;`, the optimizer rewrites them as numeric references so XML reading systems display them. The library it used for this, `entities` 7, decoded a few unknown names that extend a known one as an unrelated character. For example, `&Yumlx;` became `&#xe6f;` (a Thai character) in the optimized book instead of staying as written. Such names are rare and are errors in the source book, but the output should never change them.

`entities` 9 leaves every unknown name unchanged. A side-by-side comparison of both versions on every known name and its prefix, case and suffix variants found this single case. A regression test now covers it.

## Compatibility

- Output changes only for books containing such an unknown name: it is now kept as written.
- Font subsetting (`--fonts`) still keeps both possible glyphs for numeric references `&#128;` to `&#159;` (for example `&#150;`, displayed as an en dash by HTML parsers and as a control character by XML parsers). A new test checks this.
- Development only: the interface tests now use jsdom 31, which needs Node.js 22.22.2 or 24.15 to run the test suite. The published package still requires Node.js 22.12 or newer.

## Validation

759 unit tests pass with 4 Linux-only skips on macOS. Feature PR and post-merge CI pass on Node 22/24, including installed-package checks and EPUBCheck E2E, and native Linux AMD64/ARM64 Docker tests pass.

On one 60 MB Pages-exported book, the previous and the new dependencies produced identical extracted output in five configurations (`balanced`, `author`, `lossless`, `balanced --fonts`, `balanced --repair`, all with `--strict`), with 0 EPUBCheck errors or warnings. That book contains neither case above, so it shows only that ordinary content is unchanged.
